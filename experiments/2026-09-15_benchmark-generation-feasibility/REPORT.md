# 基于大模型生成 Python pyperf 微基准测试的可行性实验报告

## 1. 实验目标

本阶段不构建完整的多 Agent 性能优化框架，只回答两个基础问题：

1. DeepSeek 能否根据真实 Python 函数及其源码，生成可以执行的 `pyperf` 微基准测试？
2. 当生成代码出现 API、语法或运行错误时，DeepSeek 能否根据真实错误信息自动修复？

本实验是对论文 LLM4JMH 基本方法的 Python 化初步验证：将 Java/JMH 替换为 Python/pyperf，保留“生成候选测试—自动验证—反馈修复”的核心流程。本阶段不验证性能优化、不检测性能回归，也不构建完整多 Agent 系统。

## 2. 实验对象与规模

- 模型：DeepSeek V4 Pro
- 温度：0
- Python 项目：SymPy、mpmath
- 目标函数：每个项目 5 个，共 10 个
- 每个函数独立生成 3 次
- 最终样本：30 个候选 benchmark
- 每个候选最多允许 3 次自动修复

目标函数如下：

| 项目 | 目标函数 |
|---|---|
| SymPy | `expand`、`factor`、`simplify`、`diff`、`cancel` |
| mpmath | `polyval`、`quad`、`findroot`、`fsum`、`lu_solve` |

这里的“30 个样本”指 30 份独立生成的 benchmark 代码，而不是 30 个计时数据点。每份可运行 benchmark 的快速 pyperf 验证内部通常包含 20 个计时值。

## 3. 实验流程

每个样本经过以下流程：

1. 从本地环境提取目标函数源码和基本描述。
2. 将目标信息发送给 DeepSeek，生成一份完整的 pyperf benchmark。
3. 进行语法检查。
4. 进行依赖导入检查。
5. 使用 pyperf `--fast` 模式实际运行，并要求生成 JSON 结果。
6. 静态检查生成代码是否引用或调用指定目标函数。
7. 如果语法、导入、运行或目标命中失败，将真实错误信息反馈给 DeepSeek，最多修复 3 次。
8. 如果代码已经能够运行，但性能数据不稳定，则记录为“不稳定”，不要求 LLM 修改代码。
9. 最后人工检查全部 30 份最终代码，确认目标函数是否确实位于计时路径中，以及 pyperf API 是否使用正确。

需要特别区分三个判定层次：

- **可执行**：代码能够通过 pyperf 完整运行并生成结果。
- **语义正确**：真正测量了指定目标函数，且 pyperf API 使用方式正确。
- **性能稳定**：多次计时结果的波动足够小，可以支持精细的性能比较。

前两个层次回答“LLM 能否生成测试”，第三个层次回答“生成的测试质量是否足以检测微小性能变化”。

## 4. 实验结果

| 指标 | 结果 |
|---|---:|
| 初次语法通过 | 30/30（100%） |
| 初次导入通过 | 30/30（100%） |
| 初次运行通过 | 21/30（70.0%） |
| 修复后运行通过 | 29/30（96.7%） |
| 人工确认语义正确 | 28/30（93.3%） |
| 需要自动修复 | 9/30 |
| 仅按运行结果计算的修复成功 | 8/9（88.9%） |
| 人工确认的语义修复成功 | 7/9（77.8%） |
| 静态目标命中 | 25 个 True，5 个 Unknown |

初次生成时，70% 的代码可以直接运行；加入真实错误反馈和有限重试后，运行通过率提高到 96.7%。经过人工语义检查，最终有 28/30，即 93.3% 的候选可以视为真正有效的目标 benchmark。

### 4.1 各目标函数表现

| 目标函数 | 初次运行通过 | 最终语义正确 |
|---|---:|---:|
| `sympy.expand` | 1/3 | 3/3 |
| `sympy.factor` | 0/3 | 1/3 |
| `sympy.simplify` | 1/3 | 3/3 |
| `sympy.diff` | 3/3 | 3/3 |
| `sympy.cancel` | 3/3 | 3/3 |
| `mpmath.polyval` | 3/3 | 3/3 |
| `mpmath.quad` | 3/3 | 3/3 |
| `mpmath.findroot` | 2/3 | 3/3 |
| `mpmath.fsum` | 3/3 | 3/3 |
| `mpmath.lu_solve` | 2/3 | 3/3 |

`sympy.factor` 是最困难的目标：三个初始候选全部运行失败，最终只有一个候选在修复后达到语义正确。其他九个目标最终均得到 3/3 的有效 benchmark。

### 4.2 性能稳定性初步结果

实验参考论文采用 robust RSD 描述波动：

```text
robust RSD = 1.4826 × MAD / median
```

本实验暂按以下区间解释：

- robust RSD ≤ 1%：稳定
- 1% < robust RSD < 5%：中间状态
- robust RSD ≥ 5%：不稳定

在 28 个语义正确的候选中：

| 快速稳定性分类 | 数量 |
|---|---:|
| 稳定 | 0 |
| 中间状态 | 13 |
| 不稳定 | 15 |

这部分只能作为初步筛查，因为当前使用的是 pyperf `--fast` 模式，每份 benchmark 只有约 20 个计时值，而且实验运行在普通个人电脑上，并没有使用论文中的独占虚拟机环境。

因此，当前结果不能证明生成的 benchmark 已经适合检测 1% 等级的细微性能回归。

### 4.3 一个重要的假阳性

有一份 `sympy.factor` 候选通过了 pyperf 的稳定性检查，看起来是唯一的“稳定样本”。但人工审查发现，它调用 `bench_time_func` 后返回的是循环次数，而不是实际经过时间。

因此，它测得的实际上是一个近似固定值，稳定性是假的。该候选被重新判定为语义无效。

这个案例说明：

> “代码能运行”或“pyperf 没有警告”并不自动等于 benchmark 正确，仍然需要检查计时 API 的使用方式和真正的计时路径。

### 4.4 API 连接问题

原始 30 个实验槽位中，有 6 个因为 DeepSeek API 传输中断而没有取得完整模型响应。实验保留了这些失败记录，并使用相同目标、模型和参数进行补跑，最终补齐 30 个有效生成样本。

这些错误没有计入模型代码生成失败率，因为它们属于服务传输问题；但它们应该作为端到端系统可靠性的独立问题汇报。

## 5. 如何理解实验结论

### 可以得出的结论

1. DeepSeek 能够为真实 Python 函数生成可执行的 pyperf benchmark。
2. 真实错误反馈能够明显提升最终运行通过率，从 70.0% 提高到 96.7%。
3. 自动修复具有实际效果：9 个需要修复的样本中，7 个最终达到语义正确。
4. 生成代码的质量与目标函数有关；`factor` 明显比其他函数困难。
5. 只检查语法和运行不够，必须区分可执行性、语义正确性和统计稳定性。

### 不能得出的结论

1. 不能声称所有 LLM 生成的 benchmark 都是正确的。
2. 不能声称这些 benchmark 已经足够稳定，可用于检测细微性能回归。
3. 不能把结果推广到所有 Python 仓库；当前只有两个数学计算项目和十个函数。
4. 不能说明 LLM 已经能够自动优化目标代码；本阶段没有修改项目源码。
5. 不能说明完整的多 Agent 性能优化框架已经完成。

## 6. 对第一阶段问题的回答

如果老师的问题是：

> 能不能让 LLM 生成 Python 版的 pyperf 测试，并在出错后自行修复？

当前实验的回答是：

> **初步可以。** 在 30 个候选中，初次运行通过率为 70.0%；加入真实错误反馈和最多三次修复后，93.3% 的候选最终达到人工确认的语义正确。但这些 benchmark 的统计稳定性仍然不足，稳定性应作为下一阶段的独立研究问题。

## 7. 实验局限

- 样本规模仍然较小，只有 2 个项目、10 个函数。
- 两个项目都属于数值或符号计算领域，项目类型不够多样。
- 稳定性数据来自 `--fast` 快速验证，而不是正式的长期性能实验。
- 测量环境是普通 macOS 电脑，后台负载和系统调度会增加噪声。
- 静态 target-hit 分析不能识别所有局部别名，5 个 Unknown 需要人工确认。
- 当前 prompt 对 `bench_time_func` 的 API 语义约束不足，出现了一次假稳定结果。
- 当前尚未进行基线版本与优化版本的性能对比，也没有进行性能回归注入实验。

## 8. 下一步建议

下一步仍然保持小范围，不需要立即搭建多 Agent 框架：

1. 在 prompt 中明确限制 `bench_func`、`timeit` 和 `bench_time_func` 的正确用法。
2. 对当前 10 个目标重新生成一小批候选，观察语义错误率是否下降。
3. 对语义正确的代表性候选进行非 `--fast` 的正式 pyperf 测量。
4. 稳定性验证通过后，再进入“性能优化代码生成—测试—分析”的循环框架。

## 9. 汇报时可直接使用的总结

> 我们当前没有直接搭建完整的性能优化 Agent 框架，而是先验证最基础的两个能力：LLM 能否生成 pyperf benchmark，以及出错后能否根据真实错误自动修复。实验选择了 SymPy 和 mpmath 两个 Python 项目，共 10 个目标函数，每个函数独立生成 3 次，总计 30 个候选。初次生成有 70% 可以运行；经过最多三次反馈修复后，96.7% 可以运行，人工确认语义正确率为 93.3%。这说明基于 LLM 的 pyperf 生成和自动修复在技术上是可行的。不过，在 28 个语义正确的候选中，目前没有一个在快速实验下达到 robust RSD 小于等于 1% 的稳定标准。因此，本阶段证明的是“能生成、能修复”，还没有证明“生成的 benchmark 足够稳定，可用于精细性能回归检测”。

## 10. 可能被追问的问题

### 为什么是 30 个样本？

这是可行性实验，不追求论文级大规模。选择 10 个不同目标，每个重复生成 3 次，可以初步观察不同函数之间的差异以及模型生成的重复可靠性。

### 温度为 0，为什么三次生成仍然不同？

温度为 0 会降低随机性，但远程模型服务和推理过程不保证完全确定。本实验中每个目标的三份最终代码哈希均不相同。

### 为什么 29 个能运行，只有 28 个正确？

其中一份代码虽然能运行，却错误使用了 pyperf 的计时 API，得到的是伪稳定数据。因此，运行成功不能代替语义审查。

### 没有稳定样本，实验是否失败？

没有。本阶段的首要问题是“能否生成和修复 pyperf 测试”，对此结果是积极的。稳定性结果说明下一阶段必须进一步约束 benchmark 设计和改善运行环境。

### 为什么不马上做完整 Agent 框架？

因为完整框架依赖两个基础能力：生成正确的测试，以及生成正确的代码修改。如果 benchmark 本身不可靠，后面的性能优化循环也无法判断修改是否真的有效。
