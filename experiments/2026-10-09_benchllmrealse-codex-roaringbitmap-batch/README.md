本目录归档正式实验分析；框架搭建过程仍记录在根目录的 `BENCHLLM_AGENT_PROGRESS_ZH.md`。完整模型输出、补丁及运行日志保留在服务器的 `artifacts/`，未在本次整理中复制到归档。

四种输入：P1 源码和测试；P2 加问题描述；P3 加 JMH 代码；P4 两者都加。P3/P4 还开放了快速性能测试工具，因此这里比较的是“输入与工具配置组合”，不是严格的纯 Prompt 消融。

最终测量采用 5 次预热、10 次测量、2 个独立 JVM，每次 1 秒。下表保留不同工作负载，不能将 ns/op 与 ms/op 混合平均；53ba593 的一次操作包含 1000 万次 checkedAdd 调用。

## 34bce1b：位移计算（ns/op，越低越好）

| pos/count | 原版 | 开发者版 | P1 | P2 | P3 | P4 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0/1 | 4.197 | 1.501 | 1.496 | 1.390 | 1.482 | 2.500* |
| 0/2 | 6.447 | 1.458 | 1.509 | 1.402 | 1.497 | 1.396 |
| 2/1 | 4.221 | 1.476 | 1.486 | 1.379 | 1.487 | 1.381 |

P1/P3 接近开发者版本；P2 相对原版加速约 3.02–4.60 倍，相对开发者版耗时少约 4%–7%。这只是本次测量，不是可推广的 Prompt 排名。

*P4 第一项不稳定：两个 JVM 均值分别为 1.368 和 3.632 ns/op；总体 scoreError 为 1.008 ns/op。不能直接据此认定 P4 的实现更慢，需要重测。

## b5b4af6：读取容器元素数量（ns/op）

| 工作负载 | 原版 | 开发者版 | P1 | P2 | P3 | P4 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| crazyRun | 2.027 | 2.163 | 1.098 | 2.122 | 1.105 | 1.101 |
| negatedUniformHash | 9.086 | 5.947 | 1.114 | 6.049 | 1.122 | 1.119 |
| uniformHash1 | 186.145 | 173.291 | 1.111 | 173.487 | 1.117 | 1.114 |
| uniformHash2 | 186.862 | 173.917 | 1.105 | 173.461 | 1.103 | 1.099 |

P2 调整遍历索引，性能接近开发者实现；crazyRun 比原版耗时多约 4.7%，不是所有项目都提升。

P1/P3/P4 给 MappeableRunContainer 添加 cardinality 缓存；P4 还给 RunContainer 添加缓存。官方 JMH 在初始化后反复读取同一对象，没有穿插修改，所以计算结果被缓存，复杂遍历变为读一个字段。两个 uniformHash 场景相对原版约 167–170 倍加速。

这一结果不是自动判为作弊，也不能直接称为普遍性能提升。仍需验证缓存失效是否完整、反序列化/共享底层缓冲区等语义，以及“修改—查询”交替负载下的性能与额外状态成本。现有 266 个测试通过，但本次分析没有新增缓存专项测试，也没有证明补丁存在或不存在错误。

## 53ba593：checkedAdd（ms/op）

| 容器 / 数据 | 原版 | 开发者版 | P1 | P2 |
| --- | ---: | ---: | ---: | ---: |
| RUN / HALF_DUPLICATED | 94.002 | 61.592 | 62.052 | 60.380 |
| RUN / UNIQUE | 118.533 | 78.124 | 81.448 | 78.294 |
| BITMAP / HALF_DUPLICATED | 65.247 | 79.201* | 50.786 | 51.926 |
| BITMAP / UNIQUE | 81.621 | 83.986 | 66.175 | 66.483 |

P1/P2 都先检查 contains，已有元素则直接返回 false。相对原版，各场景约 1.23–1.56 倍加速；RUN 接近开发者版，BITMAP 的 UNIQUE 场景耗时比开发者版少约 21%。

需要注意：官方 JMH 的 setUp 先用完整输入数组创建 bitmap，然后 optimized 再 checkedAdd 同一数组。因此即使参数叫 UNIQUE，测量阶段的元素也全部已经存在。现有结果不能证明新元素插入、混合插入或容器转换时也更快。计时方法调用的是 RoaringBitmap，不能直接代表 MutableRoaringBitmap 的性能。

*开发者版 BITMAP/HALF_DUPLICATED 的两个 JVM 均值为 95.224 和 63.177 ms/op，scoreError 为 14.279 ms/op。不能用 79.201 的均值作稳定的开发者退化或 Agent 优势结论。

P1 还修改了 contains(subset) 的逻辑，与本题 checkedAdd 优化目标并不完全一致。虽未违反文件白名单，但后续应审核修改范围，并增加相应功能测试。

## 结论与下一步建议（尚未执行）

当前证据支持：单个 Agent 会话能够独立修改、测试，并获得部分实际性能收益；暂时没有证据要求添加固定的外层优化循环。但尚不能证明泛化正确性、某种 Prompt 总是最好，或模型普遍超过开发者。

优先顺序：

1. 不调用模型，重测两处不稳定的 JMH，保留新旧数据，不覆盖旧结果。
2. 对缓存补丁增加先查询再修改再查询、交替负载等验证；对 checkedAdd 覆盖已有/新元素/混合输入和容器转换。
3. 加强 patch 范围审核；未来将输入信息与工具权限分开控制，做真正可解释的消融。
4. 以上完成后再决定充值和补跑，不立即扩大付费批次；同时增加单次运行的上下文/步数约束与更保守的预算预留。

本次分析依据为各运行的 result.json、jmh.json、agent.patch、verification.stdout.log、codex_events.jsonl，support/manifest.json，以及评测所使用提交中的官方 JMH 源码。

## 补充功能检查结果（2026-10-09）

使用独立 Java 诊断程序对原版、开发者版和 10 个 Agent 补丁做了补充检查：

- 34bce1b：四个 Agent 的 100060 次合法输入位移比较均通过；非法参数的异常行为不同于原版，但开发者版也有同样性质的差异，先记录为兼容性问题。
- b5b4af6：随机修改/查询序列、同一对象缓存预热后的 readExternal 均通过。但 P1/P3/P4 在两个容器共享 heap/direct CharBuffer 时出现过期缓存：内容已包含两个元素，getCardinality 仍返回 1；原版、开发者版、P2 返回正确的 2。这三个缓存候选应标记为“共享缓冲区场景存在功能回归”，不能只凭官方测试通过和加速比判定成功。
- 53ba593：对普通与 Mutable 两种实现的新/重复混合添加、整数边界及数组到位图转换附近输入检查均通过。没有证明所有路径正确，P1 额外修改的 contains(subset) 仍需单独审核。

诊断源码、复现方法与适用范围见 [validation/README.md](validation/README.md)，逐版本结果见 [results/functional_probe.json](results/functional_probe.json)。原始性能结果未覆盖或修改，未修复 Agent 补丁。

## “补验证”的具体含义

不新增 Agent 外层优化循环，也不将新增测试反馈给 Agent 自动重试。保持“单个 Agent 自主修改和测试，结束后统一评测”的主流程。

- 测量复核：直接使用已有补丁重跑 JMH，不调用模型；保留重复测量数据，检查收益是否稳定。
- 功能复核：补充独立 JUnit 验收用例，例如先查询元素数量、添加/删除元素、再查询，确认缓存结果随修改更新；checkedAdd 验证新元素返回 true、重复元素返回 false，并检查内容和元素数量。优先结合项目已有相关测试，而不是另建测试框架。
- 适用范围复核：额外测“修改—查询交替”和“新元素/已有元素混合添加”等负载。在原版、Agent 版、开发者版上使用相同输入；作为独立补充评测，不替换官方 JMH、不混入官方分数。

现有结果照常保留。新增验证用于解释结果的正确性和适用范围，不是预先认定缓存优化有错。本批次实际因余额预留门槛停止；本次已实施独立功能诊断，完整的补充 JUnit、JMH 复测与其他负载性能测量尚未实施，付费任务尚未补跑。
